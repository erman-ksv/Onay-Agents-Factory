## Результат

Доверенный host может передать сохранённое отклонённое предложение и получить исправление **от модели**, а не от вручную написанного кода приложения. Исправление отправляется через прежние лимиты контекста, TPM, времени и общего бюджета, а ответ проходит прежний `prepareCalculatorRoleChanges`. Успешное предложение регистрируется в обычной команде и требует свежих Security, Reviewer и Tester; их вердикты не заменяют реальные тесты, разрешение публикации или CI.

Этот API не запускается автоматически из старых workflow или исчерпанной исторической задачи. В этой проверке использовался только подставной transport. Реальных новых запросов Groq — **0**.

## Защита от повторов и расходов

Из исходного плана, taskId, commit SHA и хеша отклонённого ответа вычисляется устойчивый executionId. Он не зависит от нового run ID, сериализации файла, номера checkpoint или настроек runtime. Проектный ledger атомарно резервирует `<executionId>:r1` до HTTP. Новый процесс, иной run ID и второй независимо авторизованный controller не получают второе резервирование для той же ошибки. Ошибки и потеря подтверждения не возвращают расходы и не вызывают автоматического повтора.

Используется настоящий одноразовый scope от существующего авторизованного controller, связанный с исходным планом и задачей. Legacy-команда без общего ledger и режим read-only не могут выполнить исправление. Сам checkpoint остаётся данными, не разрешением: внешние ожидаемые SHA256/identity должен предоставить доверенный host из проверенного удалённого барьера.

Локальные счётчики новой фазы учитывают её вызовы; предыдущие расходы остаются в полной истории общего проектного ledger. Код не обнуляет, не инициализирует и не расширяет общий grant. Применён существующий host preset с 2048 токенами ответа, максимум четырьмя запросами на фазу и общим контекстным ограничением; это технический потолок, не новое разрешение владельца.

Перед отправкой обязательны host callbacks сохранения ожидающего запроса и отклонённого ответа. Если сохранение до HTTP не удалось, резерв остаётся списанным, transport не вызывается, повторный процесс также отказывает. Отклонённое исправление помечается `kind: repair` и не становится новым исходным предложением для ещё одного исправления. Внутренний флаг попытки также запрещает дополнительный repair этой же команды.
